# Easy Gold BTL Tracker - System Documentation


This document serves as the complete technical and operational guide for the Easy Gold BTL (Below The Line) Tracker application. It covers how the web application works, the  database structure, user roles, feature details, and how to deploy the entire system from scratch to production.

## 1. System Architecture Overview

The Easy Gold BTL Tracker is a modern, serverless web application that uses Google Sheets as its primary database.

- Frontend: React + Vite
- Auth: Supabase Auth
- Database: Supabase PostgreSQL
- Backend: Cloudflare Worker only
- Live data: Supabase Realtime
- Cost: Free (CF Pages + Supabase free)
---

## 2.  Database Definition

The core of the system is the database.

### 2.1 `users` Sheet
Manages system access and authentication.
- **`username`**: The user's login email (e.g., `admin@easygold.la`).
- **`password`**: The user's password.
- **`name`**: Full name of the user.
- **`role`**: Access level (`admin`, `manager`, or `team_member`).
- **`team`**: The team the user belongs to (e.g., `KPV Team`, `Agency Team`).
- **`token`**: The active authentication session token (auto-generated by the system upon login).

### 2.2 `submissions` Sheet
The primary data table where all daily BTL marketing results are recorded.
- **`timestamp`**: ISO timestamp of when the submission was created.
- **`date`**: The date of the BTL activity (YYYY-MM-DD).
- **`team`**: The team that submitted the data.
- **`branch`**: The location/branch where the activity took place.
- **`new_register`**: Number of new user registrations acquired.
- **`new_reg_purchased`**: Number of newly registered users who made a purchase.
- **`buy_value_new`**: Total purchase value from new users.
- **`existing_users`**: Number of existing users who interacted/purchased.
- **`buy_value_existing`**: Total purchase value from existing users.
- **`footfall`**: Total estimated foot traffic passing by the booth/event.
- **`step_in`**: Number of people who stepped into the booth/event area.
- **`team_cost`**: Operational costs associated with the team for the day.
- **`merch_cost`**: Total cost of merchandise given away.
- **`merch_items`**: JSON string detailing specific merchandise distributed.
- **`lat` & `lng`**: GPS coordinates of the submission location.
- **`status`**: Current status of the submission (e.g., `active`).
- **`staff_in_charge`**: JSON string array of staff members assigned to the event.

### 2.3 `checkins` Sheet
Tracks staff check-ins at specific locations.
- **`timestamp`**: ISO timestamp of the check-in.
- **`date`**: Check-in date.
- **`team`**: Team performing the check-in.
- **`lat` & `lng`**: GPS coordinates of the check-in location.
- **`note`**: Optional notes provided by the user.

### 2.4 `targets` Sheet
Stores monthly performance targets set by management.
- **`month`**: The target month (YYYY-MM-01 format).
- **`team`**: The team the target applies to.
- **`new_reg_target`**: Target for new registrations.
- **`buy_value_target`**: Target for total purchase value.
- **`footfall_target`**: Target for foot traffic.
- **`cost_budget`**: Total allocated budget for the team.
- **`cpo_target`**: Cost Per Order target.
- **`cpa_target`**: Cost Per Acquisition target.
- **`cpao_target`**: Cost Per Acquisition & Order target.

### 2.5 `route_plan` Sheet
Planned daily routes for teams.
- **`date`**: Date of the planned route.
- **`team`**: Team assigned to the route.
- **`location_name`**: Name of the target location.
- **`lat` & `lng`**: Planned GPS coordinates.

### 2.6 `merch` Sheet
Master list of available merchandise items.
- **`itemName`**: Name of the merchandise (e.g., "Gold Flyer").
- **`cpu`**: Cost Per Unit of the merchandise.

### 2.7 `staff` Sheet
Master list of all staff members.
- **`id`**: Unique identifier for the staff member.
- **`name`**: Full name of the staff member.
- **`team`**: The team the staff member belongs to.

### 2.8 `audit_log` Sheet
System-generated log of all sensitive actions for security and tracking.
- **`timestamp`**: When the action occurred.
- **`action`**: The type of action (e.g., `submitResults`, `updateTarget`).
- **`user`**: The name of the user who performed the action.
- **`team`**: The team of the user.
- **`payload`**: JSON string of the data submitted.
- **`status`**: Success or error status.

## 3. User Roles and Permissions

The system operates with a strict Role-Based Access Control (RBAC) model.

1. **`team_member`**:
   - **Capabilities:** Can view the dashboard for their team, submit daily results, check-in, and view their assigned route plans.
   - **Restrictions:** Cannot edit past submissions (unless authorized), cannot view other teams' data, cannot change targets, settings, or manage staff/merch.

2. **`manager` (Event Manager)**:
   - **Capabilities:** Can view data for all teams, update and correct submissions, define route plans, and set monthly targets for teams. Can export Staff Reports.
   - **Restrictions:** Cannot edit system-wide settings (like Merch Cost Per Unit) or perform dangerous deletions.

3. **`admin`**:
   - **Capabilities:** Full system access. Can modify global settings (Merch lists, Staff lists), delete submissions, clear caches, and has full read/write access to all Google Sheets data.

## 4. Metrics & Calculations (Report & Dashboard)

The web app calculates real-time performance metrics (KPIs) by aggregating data from the `submissions` sheet. Here is exactly how each metric is calculated:

### 4.1 Cost Calculations
The Total Spending for a team on a given day is the sum of:
*   **Team Cost**: Operational budgets (allowances, travel, etc.) entered manually in the submission form.
*   **Merch Cost**: The automated sum of `(Quantity of Item * Cost Per Unit)` for every item selected in the "Merchandise Used" section. 
*   **Total Cost** = `Team Cost + Merch Cost`

### 4.2 Key Performance Indicators (KPIs)
When you look at the Dashboard or Submission History, the app uses the `Total Cost` and the acquired user data to calculate efficiency:

1.  **CPA (Cost Per Acquisition)**:
    *   **What it is**: How much it costs to acquire one new customer (NC).
    *   **Formula**: `Total Cost / New Registers`
    *   **Example**: If you spent ₭1,000,000 and got 50 new registers, the CPA is ₭20,000.
2.  **CPO (Cost Per Order)**:
    *   **What it is**: How much it costs to get one person to actually *buy* something.
    *   **Formula**: `Total Cost / (New Reg Purchased + Existing Users)`
    *   **Example**: If you spent ₭1,000,000 and 20 new people bought + 5 existing people bought, the CPO is ₭40,000.
3.  **CPAO (Cost Per Acquisition & Order)**:
    *   **What it is**: The blended average cost per overall successful interaction.
    *   **Formula**: `Total Cost / (New Registers + Existing Users)`
4.  **Target % Achieved**:
    *   **What it is**: How close the team is to hitting the monthly goals defined by the Manager.
    *   **Formula**: `(Actual Aggregated Metric / Target Metric from 'targets' sheet) * 100`

### 4.3 Data Filters
On the Dashboard and Report pages, the data can be filtered. Here is how the filters work internally in the code:
1.  **Date Range (Start/End)**: The app fetches *all* submissions. It then runs a JavaScript `.filter()` to only keep rows where the submission `date` falls exactly between the Start Date and End Date inputs.
2.  **Team Filter**: It applies a second `.filter()` to check if `submission.team` matches the selected dropdown. If "All Teams" is selected, this filter is skipped.
3.  **Re-calculation**: After filtering, all the mathematical formulas (Sum of Costs, Sum of Acqusitions) are re-run *only on the filtered rows*, updating the UI numbers and charts instantly without needing to reload the page.

## 5. Working Process: How Data Flows

This is the exact step-by-step process of how the web app operates, calculates data, and shows it to the user.

### Step 1: Data Entry (The Input)
*   A team member opens the **Submit Results** form on their phone or laptop.
*   They fill in the numbers (Footfall, New Registers, Existing Users).
*   They select which merchandise was used. The app instantly looks up the `Cost Per Unit` from the `merch` sheet and shows a live preview of the Merch Cost.
*   When they click "Submit", the frontend JavaScript packages this into a JSON payload and sends it to the Cloudflare API endpoint.

### Step 2: Storage (The Database)
*   The API validates the data (ensuring the user is logged in and has the right permissions).
*   It uses the database API to insert a new row at the exact bottom of the `submissions` sheet.

### Step 3: Data Retrieval (The Load)
*   When a Manager opens the **Dashboard** or **Reports** page, the frontend requests all data for the current month.
*   The backend reads the `submissions` and `targets` sheets and returns them to the browser as an array of JSON objects.


### Step 4: Calculation & Rendering (The View)
*   The frontend JavaScript receives the raw data.
*   It immediately runs the math formulas (summing all costs, calculating CPA/CPO as defined in section 4).
*   It binds these final calculated numbers to the HTML elements to show them on screen.
*   Finally, it feeds the aggregated totals into the Chart.js library to draw the donut and line charts visually.
